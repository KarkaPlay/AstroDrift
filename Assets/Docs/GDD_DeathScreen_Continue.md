## 1. Вердикт для владельца

**Брать — с двумя изменениями.** Наблюдение верное: на нынешнем Death-экране RETRY и HOME — это два пути к одному и тому же рестарту, и Rewarded-continue — стандартная, проверенная механика hyper-casual, которая здесь ложится идеально: смерть внезапна, забег короткий, «вернуть меня туда, где я умер, за просмотр рекламы» — понятный обмен без валют, магазина и прогрессии. Но в исходной идее есть две ловушки. Первая: сейчас interstitial привязан к Retry, а кнопки Retry больше не будет — точку показа interstitial надо перенести (предлагаю: тап «Домой» на Death-экране, формула та же) и добавить защиту «reward → не показывать interstitial ещё 60 секунд», иначе получится рекламная лестница, за которую Яндекс и игроки наказывают отзывами. Вторая: «продолжить с того же места» ломает текущую модель «сброс мира во время полёта камеры» — мир на Death-экране нужно заморозить и при continue чистить зону вокруг корабля с grace-периодом, иначе игрок после 30-секундной рекламы умрёт через 0.5 секунды, и механика сработает против нас. С этими правками фича маленькая по скоупу (одна кнопка, один таймер, один путь кода), метрики измеримы, и она усиливает главный цикл «умер → ещё раз» вместо того, чтобы его удлинять.

## 2. Что меняем против исходной идеи (и почему)

| Было (идея) | Стало (дизайн) | Почему |
|---|---|---|
| Retry и Home — «одно и то же», убрать Retry | Retry убирается совсем; Death-экран = предложение continue + «Домой» | владелец прав: две кнопки к одному результату — шум |
| Interstitial на Retry (текущее правило) | Interstitial переносится на тап «Домой» с Death-экрана; формула показа не меняется (§7) | Retry больше нет; interstitial должен остаться, но не может стоять сразу после reward |
| «Продолжить с того же места» | Продолжить с того же места **в замороженном мире**: чистка зоны вокруг корабля + 2 с неуязвимости + 1.5 с без спавна (§4) | защита игрока от мгновенной второй смерти — без этого continue вызывает ярость, а не благодарность |
| — | Мир на Death-экране заморожен (`Time.timeScale = 0`) | сохраняет «картину смерти» для continue и даёт игроку сидеть на экране сколько угодно |

Побочный эффект, который фиксируем честно: путь «умер → новый забег» удлиняется (Домой → меню → TAP TO PLAY ≈ 2–3 с вместо 0.6 с перелёта Retry). Это осознанный компромисс hyper-casual паттерна death→menu; intend «ещё раз» перехватывает continue-предложение.

## 3. Экономика continue

| Параметр | Значение | Комментарий |
|---|---|---|
| Continue за один забег | **1** | вторая смерть в том же забеге — Death-экран без предложения |
| Лимит за сессию/день | нет (v1) | следим по метрике `continue_used` (§8); вводить лимит только если увидим абуз |
| Цена | 1 rewarded-ролик | без роста цены: в v1 нечем платить «ростом» — не изобретаем |
| Таймер предложения | **5.0 с** | отсчёт начинается после завершения каскада (t ≈ 0.75 s от появления панели) |
| По истечении таймера | предложение + линия-таймер fade-out 0.25 s; остаётся только «Домой» | не auto-home: решение игрока не крадём |
| Отказ (тап «Домой» пока предложение висит) | обычный путь Home (+interstitial по формуле §7) | логируем `continue_declined` |

### Что сохраняется при continue

| Сохраняется | Сбрасывается / чистится |
|---|---|
| Счёт (SCORE) | Астероиды в радиусе **8 ю** от места смерти (тихо, без очков/juice) |
| Множитель (x2–x5) | Все ракеты в полёте **и все предупреждения ракет** |
| Комбо-таймер — перезапускается на полное окно (3 с) | Пули в полёте |
| Волна сложности /Elapsed `DifficultyManager` / скорость — продолжают с момента смерти | Активная неуязвимость — заменяется новой (2.0 с, §6) |
| Звёздное поле, частицы — как есть | |
| Камера стоит в кадре «место смерти, zoom-in» — при continue плавный zoom-out (§6) | |

Смысл: игрок платит за счёт и множитель, а не за «иммунитет от сложности» — волна продолжается, но старт после продолжения безопасный.

## 4. UI Death-экрана v2

### Макет (1080×1920, правило «кнопка = текст», без плашек)

```
│      S C O R E  4 250        │  Light 88 px, белый, slide +48 px
│      N E W  B E S T          │  34 px, Gold — или BEST 4 250 (#8A8A8A)
│                              │
│      П Р О Д О Л Ж И Т Ь     │  40 px, slide +24 px (каскад §4.2)
│      за просмотр рекламы     │  24 px, #8A8A8A, трекинг +8 %
│      ▁▁▁▁▁▁▁▁░░░             │  линия-таймер 2 px, убывает 5.0 s
│                              │
│      ─────────────           │  разделитель UiPanelFrame #2A2A2A
│      Д О М О Й               │  40 px, белый, slide +24 px
```

- Тап-зоны обеих кнопок — невидимые `RectTransform` ≥ 720×160 px (правило §3 арт-дирекшна).
- Между «ПРОДОЛЖИТЬ» и «ДОМОЙ» — тот же тонкий разделитель, что между старыми RETRY/HOME.
- Предложение стоит **выше** «Домой»: первое касание глаза — первый пункт каскада.

### Золото и правило §7 («не более одного золотого элемента в кадре»)

- Если **NEW BEST горит** → NEW BEST остаётся золотым (достижение), предложение — белым.
- Если **NEW BEST нет** (частый случай) → золото получает предложение «ПРОДОЛЖИТЬ» (это «живое/интерактивное» по семантике §7).
- Реализация — один условный цвет при построении каскада; вторых золотых элементов на экране нет.

### Тексты (капс, короткие)

| Элемент | RU | EN |
|---|---|---|
| Предложение | ПРОДОЛЖИТЬ | CONTINUE |
| Подпись | ЗА ПРОСМОТР РЕКЛАМЫ | WATCH AN AD |
| Выход | ДОМОЙ | HOME |
| Score / Best / New Best | без изменений (SCORE / BEST / NEW BEST — как сейчас) | — |

Локализация: в билде под Яндекс — RU-строки, EN — для стор-сборок. Механизма переключения языков не делаем (вне скоупа): строки — константами, выбор — на этапе сборки.

### Таблица состояний Death-экрана

| Состояние | Предложение | Линия-таймер | ДОМОЙ | Переход из |
|---|---|---|---|---|
| `OfferRunning` | видимо (пульс §3) | убывает 5.0 с | видимо | панель построена, реклама готова |
| `OfferExpired` | скрыто (fade-out 0.25 s) | скрыта | видимо | таймер истёк |
| `NoAd` | скрыто сразу | нет | видимо | реклама не загружена на момент смерти |
| `AdWatching` | скрыто (панель скрыта целиком) | — | — | тап по предложению; реклама на экране |
| `ContinueResumed` | — | — | — | reward получен; путь §6.2 |

Приложение ушло в фон при `OfferRunning` → таймер ставится на паузу и продолжается с того же места при возврате (§9).

## 5. Хореография: таймлайны

### 5.1 Смерть → Death-экран (изменения только в списке слоёв, кривые §4.2 без изменений)

| Слой | Действие | Длительность | Кривая | Сдвиг |
|---|---|---|---|---|
| Камера | zoom-in +15 % к месту смерти | 0.40 s | `EaseOutSoft` | 250 мс |
| HUD score | fade-out | 0.20 s | `EaseInQuick` | 0 мс |
| Death panel: Score | fade-in, slide +48 px | 0.40 s | `EaseOutSoft` | 500 мс |
| Best / NEW BEST | fade-in, slide +32 px | 0.35 s | `EaseOutSoft` | 570 мс |
| ПРОДОЛЖИТЬ + подпись + линия | fade-in, slide +24 px | 0.30 s | `EaseOutSoft` | 640 мс |
| ДОМОЙ | fade-in, slide +24 px | 0.30 s | `EaseOutSoft` | 710 мс |

Таймер предложения стартует при t = 0.78 s (сразу после каскада). Мир в этот момент уже заморожен (`Time.timeScale = 0` после slow-mo смерти): камера стоит в кадре «место смерти» сколько угодно долго — сама смерть «досматривается» в стоп-кадре, астероиды зависают. Игрок может сидеть на экране неограниченно: предложение исчезнет через 5 с, «Домой» живёт вечно.

### 5.2 Continue (reward получен) — продолжение БЕЗ рестарта

| Слой | Действие | Длительность | Кривая | Сдвиг |
|---|---|---|---|---|
| Death panel | fade-out целиком | 0.25 s | `EaseInQuick` | 0 мс |
| Корабль | появляется на месте смерти, носом вверх, мигает (неуязвимость 2.0 с) | мгновенно, под fade панели | — | 0 мс |
| Мир | чистка: астероиды ближе 8 ю, все ракеты + предупреждения, пули — тихо, без событий очков | мгновенно | — | 0 мс |
| Камера | zoom-out «кадр смерти → игровой зум» на месте (позиция не летит, только орто + композер в игровую Y) | 1.2 s | `EaseOutSoft` | 0 мс |
| HUD | fade-in 0.3 s | 0.30 s | `EaseOutSoft` | 400 мс |
| Управление | разблокировка | — | — | **t = 0.5 s** |
| Спавн угроз | возобновляется | — | — | **t ≥ 1.5 s** |

Ключевое отличие от рестарта §6.1: никакого телепорта корабля и никакого сброса мира — только локальная чистка и zoom-out камеры на месте. Камера не перелетает — она «открывает» тот же кадр.

### 5.3 Отказ / прерывание рекламы

| Ситуация | Поведение |
|---|---|
| Игрок закрыл rewarded до конца (нет награды) | возврат на Death-экран **без предложения** (только «Домой», состояние `OfferExpired`-вид): панель и кадр камеры не менялись — мир всё ещё заморожен. Никаких текстов-извинений — тишина в стиле арт-дирекшна |
| Ошибка показа (SDK) | то же, что выше; лог `continue_ad_failed` |
| Игрок тапнул «Домой» во время показа рекламы | невозможно — панель скрыта и не интерактивна (`blocksRaycasts = false`) |

### 5.4 «Домой» с Death-экрана

Существующий путь §4.5 арт-дирекшна (панель fade-out → камера 0.8 s в меню-кадр → каскад стартового UI), но перед ним — возможный interstitial (§7): переход в меню стартует строго после закрытия рекламы, по той же модели, что нынешний `RetryWithInterstitial` (сцена до рекламы не меняется).

## 6. Неуязвимость и защита от второй смерти

| Слой защиты | Число | Суммарный эффект |
|---|---|---|
| Неуязвимость + мигание | 2.0 с | игрок успевает сориентироваться |
| Чистка зоны | 8 ю от корабля (≈ ⅔ высоты экрана в игровом зуме) | вокруг корабля пусто |
| Ракеты/предупреждения | все сняты | самый нечестный убийца — наведённая ракета — не survives |
| Safe zone спавна | 1.5 с | новые угрозы не появляются |

Если игрок умирает в первые 3 с после continue (метрика `continue_died_early`) — это сигнал, что grace слаб: первым кандидатом на увеличение будет чистка 8→12 ю, вторым — неуязвимость 2.0→3.0 с. Код должен брать эти числа из `GameConfig` (§10.4), не из констант.

## 7. Реклама: пересмотр правил показа

### Rewarded (новое)

- Новый ad unit РСЯ: `R-M-19858053-3` (поле `rewardedAdUnitId`); префетч при старте приложения, перезагрузка после каждого показа/ошибки.
- Единственная точка показа — тап «ПРОДОЛЖИТЬ» на Death-экране.
- Аудио: приглушать AudioManager на время показа, возвращать после закрытия.

### Interstitial (изменение одной точки показа)

| Правило | Значение |
|---|---|
| Точка показа | тап «Домой» на Death-экране (было: Retry) |
| Формула | без изменений: `totalSessionCount > 3` И `timeSinceLastInterstitial ≥ 180 с` И `lastSessionDuration ≥ 20 с` |
| Новая защита от «лестницы» | interstitial **не показывается**, если rewarded был показан менее **60 с** назад (`rewardedQuietSeconds`) |
| Pause → Домой | без interstitial (не меняем) |
| Старт из меню | никогда не interstitial (не меняем) |

Формула 180 с сама по себе уже режет частоту, а условие 60 с после reward закрывает худший сценарий «посмотрел рекламу → закрыл рекламу → ещё реклама».

## 8. Метрики

События (все — с пропертями, где указано):

| Событие | Проперти |
|---|---|
| `death_screen_shown` | score, new_best, ad_ready |
| `continue_timer_expired` | score |
| `continue_declined` | score (тап «Домой» при живом предложении) |
| `continue_ad_started` | score, multiplier |
| `continue_ad_completed` | score, multiplier |
| `continue_ad_aborted` | закрытие без награды / ошибка показа |
| `continue_used` | score, multiplier, время жизни забега |
| `continue_survived_10s` | выжил 10 с после продолжения (1/0) |
| `continue_died_early` | смерть в первые 3 с после продолжения |
| `interstitial_home_shown` | междомное событие для сопоставления частот |

Целевые ориентиры (первая неделя после релиза):

- `continue_ad_started / death_screen_shown` ≥ **25 %** (бенчмарк Yandex hyper-casual 20–40 %).
- `continue_ad_completed / continue_ad_started` ≥ **80 %** (ниже — проблема длины ролика/фолбэка).
- `continue_survived_10s` ≥ **60 %** (ниже — усиливать grace §6).
- Динамика `interstitial_home_shown`: ожидаем просадку impressions на 10–25 % относительно Retry-показов — её должен перекрыть rewarded (eCPM rewarded обычно 2–4× interstitial). Смотрим сводку, а не каждую метрику отдельно.
- Retention D1 / длительность сессии: без негативной дельты. Если среднее число продолжений > 1.5 на игрока и сессии растут сильнее, чем retention — волна сложности «съедается» рекламой, поднимать темп после continue.

Реализация: события идут через тонкую статическую обёртку (`Analytics.Log(name, props)`), бэкенд — Яндекс AppMetrica; до интеграции SDK — `Debug.Log` в едином формате (§10.7).

## 9. Крайние случаи

| Случай | Поведение |
|---|---|
| Нет интернета / rewarded не загружен на момент смерти | предложение **скрыто целиком** (не disabled-серое): экран = Score + Best + «Домой». Таймер не запускается |
| Реклама была готова, но тап — а загрузка испортилась | `ShowRewarded` возвращает false мгновенно → возврат на Death-экран без предложения (`continue_ad_failed`). Одна попытка за смерть — повторных показов предложения нет |
| Rewarded готов, игрок ушёл в фон, сидя на Death-экране | таймер на паузе (unscaled-время не течёт в фоне); по возврату — с того же места |
| Игрок сворачивает приложение во время показа rewarded | обрабатывает SDK; наша игра всё равно заморожена, сцене ничего не грозит |
| Повторное использование | 1 продолжение за забег; после продолжения и повторной смерти — экран без предложения |
| Приложение убито системой во время rewarded | ничего не теряется: счёт не персистится между сессиями (кроме рекорда — он уже сохраняется в `ScoreManager`) |
| Сессия/рекламные счётчики | смерть инкрементит `totalSessionCount` (как сейчас); continue вызывает `ResumeSession()`, который откатывает инкремент и возвращает сессию в активное состояние — иначе забег посчитается дважды и собьётся grace-формула (§10.1) |

## 10. ТЗ ДЛЯ UNITY DEVELOPER

> Все новые числа — только в [GameConfig.cs](Assets/Scripts/Core/GameConfig.cs) (правило проекта «тюнинг без кода»). Все анимации — unscaled time, две канонические кривые из [UiAnim.cs](Assets/Scripts/UI/UiAnim.cs). Ни одного мгновенного `SetActive(true)` на видимых панелях.

### 10.1 [YandexAdsManager.cs](Assets/Scripts/Ads/YandexAdsManager.cs) — Rewarded API

Сегодня в классе есть только banner + interstitial. Добавить:

1. **Поле** `[SerializeField] private string rewardedAdUnitId = "R-M-19858053-3";` (demo-ID → реальный из партнёрского интерфейса РСЯ).
2. **Загрузка** (Android, `#if UNITY_ANDROID && !UNITY_EDITOR`, по образцу `RequestInterstitial`): `RewardedAdLoader` → `RewardedAd`; префетч в `Start()`, перезагрузка после показа/ошибки. Подписки: `OnRewardedAdRewarded`, `OnAdDismissed`, `OnAdFailedToShow`, loader-ошибки — с тем же стилем логов `[YandexAds]`.
3. **Публичное API**:
   - `public bool IsRewardedReady { get; }` — true, только если объект загружен.
   - `public void ShowRewarded(Action<bool> onResult)` — НЕ блокирует: если не загружен → `onResult(false)` синхронно. Иначе показ; `onResult(true)` — только если прилетел `OnRewardedAdRewarded` (награда выдана), `onResult(false)` — при dismissed-без-награды / failed-to-show. Колбэк — строго один раз.
   - **Editor-заглушка**: fake-показ = 2.0 с ожидания (`WaitForSecondsRealtime`), лог, `onResult(true)`.
4. **Сессии**: `public void ResumeSession()` — откатывает инкремент `totalSessionCount`, сделанный последним `RegisterSessionEnd()` (сохранять значение счётчика на момент смерти), и возвращает `_sessionActive = true` с тем же `_sessionStartRealtime` (длительность забега считается с первичного старта). Вызывается из `GameManager` при continue. Критерий: `totalSessionCount` растёт ровно на 1 за фактически завершённый забег.
5. **Защита от лестницы**: хранить `lastRewardedTimestamp` (Unix-сек, строкой, как `PrefsLastInterstitial`); в `PassesFrequencyFormula` добавить четвёртое условие `sinceLastRewarded >= 60` (из нового поля `GameConfig.rewardedQuietSeconds`). Лог причины отказа — расширить существующий.
6. **Аудио**: перед показом rewarded — mute, после `onResult` — unmute (через `AudioManager.Instance`, если жив).

Критерии приёмки 10.1:
